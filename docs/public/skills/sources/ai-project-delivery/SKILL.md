# AI 项目交付

把一个开发想法变成可验证的代码交付。适用于 Codex、Claude Code、Cursor 等能够读取 Agent Skill 的工具。此 Skill 提供工作方法，不会自动赋予终端、浏览器、网络或部署权限。

## 目标与原则

最终交付必须说明：改了什么、为什么改、如何验证、哪些内容尚未验证、如何回滚。不要把“代码已写出”当成“功能已完成”。

- 先理解仓库现状，再决定改动；优先复用已有架构与约定。
- 小步实施，每一步都尽可能能验证；不为未提出的需求扩大范围。
- 区分事实、假设和待确认事项；遇到影响数据、权限、账单或线上环境的操作先请求确认。
- 不伪造测试结果、构建结果、截图、部署状态或外部服务响应。
- 不读取、输出或提交密钥；不将环境变量、令牌、用户数据写入日志或示例。

## 阶段 1：澄清需求

将用户请求整理为一份简短的交付简报：

1. **目标**：用户最终想完成什么，谁会使用。
2. **验收标准**：最多列出 3–7 条可观察、可验证的结果。
3. **范围**：本次包含什么；明确不做什么。
4. **约束**：技术栈、兼容性、性能、安全、时间或已有设计。
5. **风险**：是否涉及数据库迁移、认证、付费、隐私数据、破坏性操作或生产部署。

如果缺少的信息不会改变实现方向，采用最保守的合理默认值并记录假设。若缺失信息可能导致数据丢失、权限扩大、费用产生或生产故障，先提问，不要猜。

## 阶段 2：勘察代码库

在修改前：

- 查看项目说明、目录结构、依赖清单、入口文件、相关模块和测试命令。
- 检查工作区状态与近期相关改动；不要覆盖用户未提交的修改。
- 搜索已有实现、相似组件、命名约定和错误处理方式。
- 确认当前运行、构建和测试的基线；若无法执行，记录原因。
- 列出准备修改的文件及其作用。

禁止为了“更干净”而重写无关模块。发现问题与本次目标无关时，单独报告，不顺手扩大改动。

## 阶段 3：制定实施计划

将工作拆成小任务，每个任务包含：

- 要修改的行为或文件；
- 可能影响的模块；
- 验证方法；
- 失败时的恢复方式。

优先选择最小可行改动。对于高风险操作，先提供方案和影响说明，等待用户确认。涉及第三方依赖时，检查维护状态、许可证、版本兼容和必要性，不为小功能随意引入新依赖。

## 阶段 4：实施

按计划逐项修改：

1. 先实现最小闭环，再处理边界情况。
2. 遵循项目已有风格，不擅自改变公共 API、数据格式或配置约定。
3. 对输入做校验，对失败给出可操作的错误信息。
4. 涉及安全、认证、权限、文件路径或外部输入时，考虑越权、注入、泄漏和误操作。
5. 仅在确有必要时新增依赖、脚本或配置，并解释理由。
6. 完成一个逻辑单元后先检查 diff，发现偏离范围立即收敛。

## 阶段 5：验证

从低成本到高成本执行适用的检查：

1. 静态检查：格式、类型、lint 或配置校验。
2. 单元测试：覆盖新增逻辑与关键边界。
3. 集成测试：检查模块间交互、数据格式和错误路径。
4. 构建检查：确认项目能按既有命令构建。
5. 端到端或手工验收：按需求逐条检查用户可见行为。
6. 安全检查：确认没有密钥、个人数据、危险默认值或不必要权限进入改动。

报告每项检查的真实状态：`通过`、`失败`、`未运行`。如果某项无法运行，写明原因与剩余风险。不能用“看起来没问题”替代验证。

## 阶段 6：代码审查与收尾

检查最终 diff：

- 是否只改了本次需要的文件；
- 是否留下调试代码、死代码、占位内容或无用依赖；
- 是否有异常路径未处理；
- 是否更新必要的文档、测试和示例；
- 是否会破坏旧配置、现有数据或兼容性；
- 是否有任何未经授权的线上操作。

若有 Git 可用，提供变更摘要和相关提交信息；未经用户明确要求，不擅自推送、合并或发布。

## 阶段 7：交付报告

按以下模板输出，避免冗长：

### 结果
一句话说明完成了什么。

### 变更
- 文件/模块：变更内容与原因。

### 验证
- 检查项：通过 / 失败 / 未运行，附实际命令或证据。

### 未解决事项
列出已知限制、未验证部分和可能影响。

### 下一步
只提出最有价值的 1–3 项后续动作。

## 特殊场景

- **Bug 修复**：先复现或明确故障证据，再修复；新增回归测试，避免只掩盖症状。
- **新功能**：先实现最小用户路径，再覆盖空状态、失败状态和边界输入。
- **重构**：先锁定现有行为与测试基线，确保外部行为不变。
- **依赖升级**：检查破坏性变更、锁文件和构建结果；不要批量升级无关依赖。
- **部署**：部署前确认目标环境、变更范围、迁移和回滚方案；只有收到真实部署结果后才能声称已上线。
- **用户要求“直接做”**：能安全推进的步骤直接执行；涉及破坏性操作、隐私、权限、付费或生产变更时先确认。

## 验收清单

- [ ] 需求与验收标准清楚，假设已记录。
- [ ] 修改前已勘察代码库与现有约定。
- [ ] 改动范围与目标一致，没有无关重写。
- [ ] 新增逻辑有适当测试或明确的替代验证。
- [ ] 已执行可运行的检查，未运行项如实标注。
- [ ] 没有提交密钥、敏感数据或未授权的生产操作。
- [ ] 交付报告区分已完成、未完成和未验证事项。
